# Voice AI Manager — состояние системы

Документ описывает, что в системе **работает по-настоящему**, что является
**детерминированной заглушкой**, и что **ещё не реализовано**. Это не план и не
обещание — только фактическое состояние кода на текущий момент.

## Итог одной строкой

Control-plane (состояния звонка, бронирование, доставка событий, безопасность,
изоляция арендаторов) реализован поверх Postgres и покрыт тестами.
Медиа-тракт (телефония, STT, LLM, TTS) — заглушки. Реальные звонки система
принимать не может и намеренно отказывается это делать.

---

## 1. Что работает по-настоящему

| Область | Реализация | Тесты |
| --- | --- | --- |
| Подпись вебхуков | HMAC-SHA256 + `timingSafeEqual`, канонизация `v1:timestamp:body` | да |
| Защита от replay | Окно допустимого времени + уникальность `(company, source, event_id)` в БД | да |
| Идемпотентность вебхуков | Постоянная (таблица `voice_inbound_events`), выживает рестарт | да |
| Изоляция арендаторов | Каждый запрос и каталог услуг скоупятся по `company_id` | да |
| Бронирование | Двухфазное `hold → confirm`, защита от двойной брони частичным уникальным индексом | да |
| Идемпотентность брони | Уникальный `(company_id, idempotency_key)`; повтор возвращает ту же запись | да |
| Очередь событий (outbox) | Атомарный захват `FOR UPDATE SKIP LOCKED`, exponential backoff, dead-letter | да |
| Восстановление после сбоя | `reclaimStaleEvents` возвращает захваты упавшего воркера | да |
| Режимы работы | `demo / test / live / degraded / disabled` + preflight gate | да |
| Ограничение частоты | Token bucket на арендатора, отдаёт `Retry-After` | да |
| Редакция PII | Маскирование телефонов, имён, e-mail перед логом и аудитом | да |
| Метрики латентности | Пофазный тайминг тёрна + перцентили (p50/p90/p95) | да |
| Аудит | Таблица `voice_audit_log`, пишется на ключевых переходах | да |

Всего 118 тестов, включая интеграционные против реального Postgres:
конкурентная гонка за слот и конкурентный захват события из очереди.

## 2. Что является заглушкой

Заглушки **детерминированы** (без случайности) и явно помечены в коде. Они
позволяют прогонять сценарии целиком, но не обрабатывают реальный звук.

- **Телефония** — нет провайдера, нет SIP, нет медиапотока.
- **STT** — нет распознавания речи.
- **LLM** — ответы берутся из сценарного движка, а не от модели.
- **TTS** — синтеза речи нет.
- **CRM / календарь / мессенджеры** — записи ставятся в `pending_retry`,
  наружу ничего не уходит.
- **Каталог услуг** — `DEFAULT_CATALOG` в коде; скоупится по компании, но не
  хранится в БД.

## 3. Что не реализовано

- Потоковый аудиотракт: WebSocket-транспорт, VAD, barge-in, детекция конца
  реплики. Интерфейсы и метрики под это есть, самого тракта нет.
- Отдельный Node-сервис голосового шлюза (согласован, но не написан).
- Мультиязычность сверх маршрутизации по коду языка.
- Deployment-kit: Docker, systemd, обратный прокси.
- Панель управления dead-letter в UI (API есть, интерфейса нет).

## 4. Модель безопасности

**Секрет вебхука не хранится в базе.** HMAC требует секрет в открытом виде, а
по SHA-256-хешу подпись проверить невозможно. Поэтому:

- секрет живёт в переменной окружения `VOICE_CONTROL_CENTER_SECRET`;
- в БД (`voice_companies.webhook_secret_hash`) лежит только хеш — для аудита и
  контроля ротации, не для проверки подписи.

**Fail-closed.** Если секрет не задан, маршруты вебхука и доставки возвращают
`503` и не обрабатывают ничего. Незащищённый режим отсутствует.

### Необходимые переменные окружения

| Переменная | Назначение | Без неё |
| --- | --- | --- |
| `DATABASE_URL` | Postgres (Neon) | приложение не работает |
| `VOICE_CONTROL_CENTER_SECRET` | HMAC входящих и исходящих вебхуков | вебхуки и доставка отдают `503` |
| `CRON_SECRET` | Авторизация запуска воркера доставки | очередь не разгружается |

Сгенерировать секреты: `openssl rand -hex 32`.

> Сейчас `VOICE_CONTROL_CENTER_SECRET` и `CRON_SECRET` **не заданы**, поэтому
> тракт Control Center намеренно неактивен.

## 5. Режимы и preflight gate

| Режим | Смысл |
| --- | --- |
| `demo` | Заглушки, произвольные номера. Безопасен по умолчанию. |
| `test` | Заглушки, только номера из allowlist. |
| `live` | Реальные звонки. Требует пройденный preflight. |
| `degraded` | Приём с урезанной функциональностью. |
| `disabled` | Полный отказ обслуживания. |

Переход в `live` проверяется `preflight()` и **блокируется**, пока не настроены
реальные провайдеры. Это не декоративная проверка: сейчас она не пропускает
`live`, потому что медиа-тракт отсутствует.

## 6. Проверка

```bash
pnpm typecheck    # строгая типизация
pnpm test         # 118 тестов
pnpm verify       # то же одной командой
pnpm build        # production-сборка
```

Интеграционные тесты требуют `DATABASE_URL`; при её отсутствии они
самоисключаются, а не падают ложно.

```bash
# состояние системы, готовность к live, статистика очереди
curl /api/voice/health
```

## 7. Найденные и исправленные дефекты

Дефекты, обнаруженные тестами в ходе этой работы, — не гипотетические:

1. **Гонка за слот маскировалась под сбой провайдера.** Drizzle оборачивает
   ошибку драйвера, поэтому код Postgres `23505` лежал в цепочке `cause`, а не
   на верхнем уровне. Занятый слот выглядел как `provider_unavailable`
   (повторяемая ошибка), и вызывающий код повторял запрос вместо предложения
   другого времени. Тот же дефект ломал идемпотентность брони — повтор мог
   привести к двойной записи.
2. **Двойная доставка событий.** `claimDueEvents` только читал строки, не
   захватывая их: два воркера или наложившиеся запуски cron отправили бы одно
   событие дважды. Исправлено на `FOR UPDATE SKIP LOCKED`.
3. **Событие могло зависнуть навсегда.** Если вебхук компании не настроен,
   событие оставалось в статусе `delivering`, а захват выбирает только
   `pending` — событие не доставилось бы никогда.
4. **Cron не сработал бы.** Vercel Cron присылает `GET`, а маршрут принимал
   только `POST`.
5. **Утечка каталога между арендаторами.** Интерфейс принимал `companyId`, но
   реализация его игнорировала и отдавала общий каталог всем компаниям.
6. **Потолок задержки не был потолком.** Джиттер применялся вверх и превышал
   `capMs`.
7. **Риск SQL-инъекции.** В разборе dead-letter идентификаторы подставлялись в
   строку запроса; заменено на параметризованный `inArray`.
